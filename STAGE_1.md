# STAGE 1 — ДОРАБОТКА TELEGRAM-БОТА ДЛЯ КЛИНИНГА

> Главная цель Stage 1 — не написать отдельные функции, а довести существующий Telegram-бот до полностью рабочего состояния по всем требованиям этого документа.
>
> Этот файл является основным чеклистом Stage 1. Все пункты обязательны.
>
> Нельзя считать Stage 1 завершённым только потому, что код был изменён. Каждый пункт необходимо проверить на фактическом рабочем сценарии.

---

# 0. ГЛАВНЫЕ ПРАВИЛА РАБОТЫ

## 0.1. ОБЯЗАТЕЛЬНО ИЗУЧИТЬ ПРОЕКТ ДО ИЗМЕНЕНИЙ

Перед написанием любого кода:

1. Изучи весь существующий проект.
2. Изучи структуру проекта.
3. Найди точку запуска бота.
4. Изучи существующую архитектуру.
5. Изучи существующую БД и модели.
6. Изучи FSM/state.
7. Изучи handlers.
8. Изучи callback_data.
9. Изучи keyboards.
10. Найди существующий клиентский flow оформления заказа.
11. Найди существующую админку.
12. Найди существующий интерфейс исполнителя.
13. Найди существующие статусы заказов.
14. Найди существующую систему пользователей.
15. Найди существующую систему фотографий.
16. Найди существующий расчёт стоимости, если он уже существует.
17. Определи, какие требования уже реализованы.
18. Определи, какие требования реализованы частично.
19. Определи, какие требования отсутствуют.
20. Определи существующие проблемы и регрессии.

Не начинай массовое переписывание проекта до понимания существующей архитектуры.

---

# 0.2. НЕ СОЗДАВАТЬ ДУБЛИКАТЫ

Если необходимая система уже существует:

- доработай её;
- не создавай вторую аналогичную систему.

Особенно это касается:

- заказов;
- пользователей;
- исполнителей;
- статусов;
- FSM;
- админки;
- клавиатур;
- фотографий;
- БД;
- расчёта стоимости.

Не создавать вторую таблицу заказов, если уже существует таблица заказов.

Не создавать вторую FSM для того же сценария без необходимости.

Не создавать вторую админку.

Не создавать параллельную систему статусов.

---

# 0.3. НЕ ЛОМАТЬ РАБОТАЮЩИЙ ФУНКЦИОНАЛ

Изменения должны быть совместимы с существующей системой.

После изменений обязательно проверить:

- запуск бота;
- регистрацию;
- основное меню;
- существующую навигацию;
- существующие услуги;
- существующие заказы;
- БД;
- админку;
- исполнителей;
- существующие callback;
- существующие FSM;
- существующие команды.

Если изменение ломает старый функционал — исправить до завершения Stage 1.

---

# 0.4. НИКАКИХ ЗАГЛУШЕК

Запрещено:

- создавать fake-функции;
- создавать mock вместо реальной логики;
- имитировать сохранение данных;
- показывать фиктивные заказы;
- создавать фиктивных исполнителей;
- создавать фиктивные рейтинги;
- создавать фиктивные отзывы;
- писать сообщения о том, что функция работает, если она фактически не работает.

Функция должна быть подключена к реальной системе.

---

# 0.5. КРИТЕРИЙ «ГОТОВО»

Пункт считается выполненным только если:

1. функционал реализован;
2. он подключён к реальному flow;
3. кнопки работают;
4. переходы работают;
5. данные корректно сохраняются;
6. данные корректно читаются;
7. нужные роли получают доступ;
8. ограничения доступа работают;
9. ошибки обрабатываются;
10. выполнена фактическая проверка;
11. существующий функционал не сломан.

Наличие кода само по себе не является доказательством выполнения.

---

# 0.6. ПРАВИЛО ИСПРАВЛЕНИЯ ОШИБОК

Если во время проверки найдено:

- неработающая кнопка;
- неправильный callback;
- зависание;
- неправильный переход;
- ошибка FSM;
- ошибка БД;
- неправильное отображение;
- отсутствие фотографии;
- неправильный статус;
- неправильное уведомление;
- неправильное сохранение данных;

необходимо:

1. найти причину;
2. исправить причину;
3. повторить сценарий;
4. проверить результат;
5. проверить отсутствие регрессии.

Нельзя просто записать найденную проблему в отчёт и оставить её, если она входит в область Stage 1 и не заблокирована внешней причиной.

---

# 0.7. СТАТУСЫ ПРОВЕРКИ

Использовать только три статуса:

### PASS

Функционал полностью реализован и реально проверен.

### FAIL

Функционал отсутствует, работает неправильно или реализован частично.

### BLOCKED

Функционал невозможно реализовать или проверить из-за конкретной внешней причины.

Для BLOCKED обязательно указать:

- что именно заблокировано;
- причина;
- чего не хватает;
- что необходимо для продолжения.

Нельзя использовать:

- «почти готово»;
- «в целом работает»;
- «должно работать»;
- «по коду всё правильно».

---

# 1. КЛИЕНТСКОЕ ОФОРМЛЕНИЕ ЗАКАЗА

Клиент должен иметь возможность полностью оформить заказ через Telegram-бота.

Обязательный flow:

Услуга
→ дата
→ время
→ адрес
→ телефон
→ комментарий
→ фотографии
→ предпросмотр
→ редактирование
→ подтверждение
→ создание заказа.

Проверить:

- каждый шаг;
- переход назад;
- отмену;
- повторное нажатие кнопок;
- обязательные поля;
- сохранение данных.

---

# 2. ВЫБОР УСЛУГИ

Клиент должен видеть доступные услуги.

Для услуги показывать:

- название;
- описание;
- стоимость или ориентировочную стоимость;
- что входит в услугу.

После выбора услуга должна сохраняться в текущем заказе.

---

# 3. ВЫБОР ДАТЫ

Добавить удобный выбор даты.

По возможности использовать кнопки/календарь.

Не заставлять клиента вручную вводить дату без необходимости.

После выбора:

- дата должна сохраниться;
- дата должна отображаться в предпросмотре;
- дата должна отображаться в заказе;
- дата должна быть доступна администратору;
- дата должна быть доступна исполнителю.

Проверить корректность переходов после выбора даты.

---

# 4. ВЫБОР ВРЕМЕНИ

Добавить выбор доступного времени через кнопки.

Проверить:

- кнопки времени;
- сохранение выбранного времени;
- отображение времени;
- переход к следующему шагу.

Если время недоступно — клиент не должен иметь возможность выбрать его как доступное.

---

# 5. АДРЕС

Клиент должен указать адрес.

Адрес должен:

- сохраняться;
- отображаться в предпросмотре;
- отображаться администратору;
- отображаться исполнителю.

Проверить корректную обработку ввода.

---

# 6. НОМЕР ТЕЛЕФОНА

Добавить отдельную кнопку:

**«Указать номер телефона»**

Использовать стандартную возможность Telegram отправить контакт.

Полученный номер:

- сохранить;
- показать в предпросмотре;
- показать администратору;
- показать исполнителю.

Проверить обработку корректного и некорректного ввода.

---

# 7. КОММЕНТАРИЙ

Клиент должен иметь возможность оставить комментарий к заказу.

Комментарий:

- сохранить;
- показать в предпросмотре;
- показать администратору;
- показать исполнителю.

Если комментарий необязателен — клиент должен иметь возможность пропустить этот шаг.

---

# 8. ФОТОГРАФИИ ПОМЕЩЕНИЯ

Клиент должен иметь возможность прикрепить фотографии помещения.

Требования:

- фотографии должны сохраняться;
- фотографии должны быть связаны с конкретным заказом;
- фотографии должны быть доступны администратору;
- фотографии должны быть доступны назначенному исполнителю;
- фотографии не должны смешиваться с фотографиями других заказов.

Проверить отправку:

- одной фотографии;
- нескольких фотографий;
- нескольких сообщений подряд.

---

# 9. ПРЕДПРОСМОТР ЗАКАЗА

Перед подтверждением показать полный предпросмотр.

Показывать:

- услугу;
- дату;
- время;
- адрес;
- телефон;
- комментарий;
- фотографии;
- стоимость/ориентировочную стоимость.

Добавить возможность:

- изменить услугу;
- изменить дату;
- изменить время;
- изменить адрес;
- изменить телефон;
- изменить комментарий;
- изменить фотографии.

После редактирования снова показать актуальный предпросмотр.

---

# 10. ПОДТВЕРЖДЕНИЕ ЗАКАЗА

После подтверждения:

1. создать реальный заказ;
2. сохранить данные в БД;
3. присвоить заказу ID;
4. установить начальный статус;
5. уведомить администратора;
6. очистить временное состояние заказа;
7. показать клиенту результат создания заказа.

Нельзя создавать несколько заказов при повторном нажатии кнопки подтверждения.

---

# 11. ОТМЕНА ОФОРМЛЕНИЯ

Клиент должен иметь возможность отменить оформление заказа.

После отмены:

- временные данные должны корректно очиститься;
- пользователь должен выйти из FSM;
- бот должен вернуть пользователя в нормальную навигацию.

Не должно создаваться незавершённого заказа в БД.

---

# 12. ОТМЕНА СОЗДАННОГО ЗАКАЗА

Если текущая бизнес-логика разрешает отмену:

- клиент должен иметь кнопку отмены;
- статус должен измениться на «Отменён»;
- администратор должен получить уведомление;
- исполнитель не должен продолжать считать заказ активным.

Повторная отмена уже отменённого заказа не должна ломать систему.

---

# 13. СТАТУСЫ ЗАКАЗА

Использовать единую систему статусов.

Минимальные статусы:

- Новый;
- Принят;
- Назначен исполнитель;
- В работе;
- Выполнен;
- Отменён.

Если система статусов уже существует — использовать её.

Проверить:

- изменение статуса;
- отображение статуса клиенту;
- отображение статуса исполнителю;
- отображение статуса администратору;
- сохранение статуса в БД;
- корректность переходов.

---

# 14. «МОИ ЗАКАЗЫ»

Добавить/доработать:

**«Мои заказы»**

Клиент должен видеть свои заказы.

Для каждого заказа:

- ID;
- услуга;
- дата;
- время;
- адрес;
- исполнитель;
- стоимость;
- статус.

Не показывать пользователю чужие заказы.

---

# 15. ИСТОРИЯ ЗАКАЗОВ

Завершённые и отменённые заказы должны сохраняться.

Клиент должен иметь возможность открыть историю.

При открытии старого заказа показывать актуальные сохранённые данные.

---

# 16. ПОВТОРНЫЙ ЗАКАЗ

Для завершённого заказа добавить:

**«Повторить заказ»**

Использовать старые данные как основу нового заказа.

Перед созданием нового заказа дать возможность изменить:

- услугу;
- дату;
- время;
- адрес;
- телефон;
- комментарий;
- фотографии.

Не создавать копию старого заказа вместо нового.

Новый заказ должен получить новый ID.

---

# 17. ОЦЕНКА КЛИНИНГА

После выполнения заказа клиент должен иметь возможность поставить оценку:

**1–5**

Опционально добавить текстовый отзыв.

Оценка должна быть связана с:

- заказом;
- клиентом;
- исполнителем.

Не разрешать выставить несколько независимых оценок одному завершённому заказу без предусмотренной логики изменения оценки.

---

# 18. РЕЙТИНГ ИСПОЛНИТЕЛЕЙ

Рейтинг должен рассчитываться на основе реальных оценок.

Не использовать фиктивные оценки.

Проверить:

- сохранение оценки;
- пересчёт рейтинга;
- отображение рейтинга;
- связь рейтинга с исполнителем.

---

# 19. ИСПРАВЛЕНИЕ ПРОБЛЕМЫ С ОТЧЕСТВОМ

Найти причину существующей проблемы с полем отчества.

Не просто скрывать поле.

Проверить:

- FSM;
- модели;
- БД;
- валидацию;
- отображение;
- регистрацию;
- редактирование профиля.

Исправить реальную причину.

---

# 20. СВОРАЧИВАНИЕ МЕНЮ

Во время оформления заказа основное меню не должно мешать текущему шагу.

На каждом шаге показывать только необходимые действия.

После:

- завершения;
- подтверждения;
- отмены;

вернуть пользователя в нормальную навигацию.

---

# 21. ИНТЕРФЕЙС

Привести интерфейс к единому стилю.

Использовать:

- понятные названия;
- единые кнопки;
- умеренные эмодзи;
- жирный текст для важных элементов;
- понятные сообщения об ошибках.

Не перегружать интерфейс.

---

# 22. ЖИРНЫЙ ТЕКСТ

Использовать жирный текст для:

- названия услуги;
- стоимости;
- даты;
- времени;
- статуса;
- важных действий;
- ключевых преимуществ.

Не делать весь текст жирным.

---

# 23. ИНТЕРФЕЙС ИСПОЛНИТЕЛЯ

Исполнитель должен иметь отдельный интерфейс.

Он должен видеть только свои назначенные заказы.

В заказе:

- услуга;
- дата;
- время;
- адрес;
- телефон клиента;
- комментарий;
- фотографии клиента;
- стоимость;
- статус.

Исполнитель не должен получать доступ к чужим заказам.

---

# 24. НАЗНАЧЕНИЕ ИСПОЛНИТЕЛЯ

Администратор должен иметь возможность:

1. открыть заказ;
2. увидеть доступных исполнителей;
3. выбрать исполнителя;
4. назначить его;
5. сохранить назначение;
6. уведомить исполнителя.

После назначения:

- исполнитель видит заказ;
- клиент видит исполнителя;
- администратор видит назначение.

---

# 25. ДОБАВЛЕНИЕ ИСПОЛНИТЕЛЯ

Администратор должен иметь возможность добавить нового исполнителя.

При добавлении указать:

- имя;
- Telegram ID;
- статус доступности;
- рейтинг, если он предусмотрен бизнес-логикой.

После добавления исполнитель должен появиться в системе.

Администратор должен иметь возможность:

- редактировать исполнителя;
- изменять доступность;
- удалить/деактивировать исполнителя;
- просматривать его рейтинг;
- просматривать его заказы.

Удаление исполнителя не должно удалять историю уже выполненных заказов.

Если физическое удаление ломает историю — использовать деактивацию.

---

# 26. ДОСТУПНОСТЬ ИСПОЛНИТЕЛЯ

У исполнителя должен быть статус доступности.

Минимально:

- доступен;
- недоступен.

Недоступного исполнителя нельзя назначить на новый заказ, если текущая бизнес-логика требует проверки доступности.

---

# 27. ФОТО ПОСЛЕ ВЫПОЛНЕНИЯ

Исполнитель должен иметь возможность отправить фотографии результата.

Фотографии:

- привязать к заказу;
- сохранить;
- показать администратору;
- показать клиенту.

Не смешивать фотографии результата с фотографиями помещения клиента.

---

# 28. ЗАВЕРШЕНИЕ ЗАКАЗА

Исполнитель должен иметь возможность завершить заказ.

При завершении:

- статус меняется на «Выполнен»;
- дата/время завершения сохраняются;
- администратор получает уведомление;
- клиент получает уведомление;
- клиенту становится доступна оценка.

Нельзя завершить чужой заказ.

---

# 29. АДМИНКА — ЗАКАЗЫ

Администратор должен иметь возможность:

- видеть новые заказы;
- видеть активные;
- видеть назначенные;
- видеть заказы в работе;
- видеть выполненные;
- видеть отменённые;
- открыть любой заказ;
- увидеть все данные;
- увидеть фотографии;
- изменить статус;
- назначить исполнителя.

---

# 30. АДМИНКА — ИСПОЛНИТЕЛИ

Администратор должен иметь отдельный раздел исполнителей.

Возможности:

- список исполнителей;
- добавить;
- открыть;
- изменить;
- изменить доступность;
- деактивировать;
- просмотреть рейтинг;
